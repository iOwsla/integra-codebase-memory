# v0.1.0-alpha.36 — Fast search_code on large projects

After alpha.35 was installed, `search_code` for a common word took about 1.2 s
on a 5,660-file project, and a rare or absent term about 0.4 s. PostgreSQL
cannot estimate how often a substring occurs in file content. For a common word
it decompressed every trigram candidate; for a long rare pattern it walked
every file. Refreshing statistics changed neither plan. The alpha.35 notes said
a common word took 2–15 ms; that held only when the planner happened to choose
the path order.

`search_code` now chooses the access order itself. It walks growing path
windows while matches are dense. Once the observed density makes rechecking the
estimated trigram candidates cheaper than walking on, it reads the remaining
candidates in path order and stops when the page is full. Both stages read
files in path order, so results, offsets and `hasMore` are unchanged.

Migration 15 replaces the content trigram index with one led by
`repository_id` (`btree_gin`), so a project's candidates no longer include
other projects' files.

Measured on a copy of the live index (8,853 files in two projects), median of
five runs, every page equal to the alpha.35 result:

| | alpha.35 | alpha.36 |
| --- | --- | --- |
| 5,660-file project, common word, first page | 0.75–1.23 s | 2–8 ms |
| 5,660-file project, rare or absent term | 0.38–0.42 s | 14–22 ms |
| 5,660-file project, slowest of 45 pages | 1.27 s | 0.34 s |
| 3,193-file project, rare or absent term | 120–142 ms | 6–16 ms |

## Update

On macOS/Linux, run `codememory update --version v0.1.0-alpha.36`. On Windows,
use `codememory.cmd update --version v0.1.0-alpha.36`. Reconnect open MCP
clients after updating. Migration 15 runs during the update: it creates the
`btree_gin` extension (trusted in PostgreSQL 13 and later) and rebuilds one
index, about 5 s for 8,800 files. The analyzer version is unchanged, so
projects do not re-analyze.

## Validation and limits

On macOS, lint, typecheck and build passed. All 361 tests across 65 files
passed, as did the upgrade acceptance script. The existing result-equality
suite passed with three new cases. A new test checks that a sparse term uses
trigram candidates and a dense term a single path window.

Some deep or unusual pages are slower. On the 3,193-file project, `prisma.`
appears in none of the first 520 files in path order; its first page went from
16 ms to 62 ms. A page at offset 500 for `service` on the larger project went
from 185 ms to 338 ms. The cost ratio between the two stages was measured on
these two projects only. The tagged Linux, Windows and macOS release workflow
must pass before GitHub publishes this prerelease.
